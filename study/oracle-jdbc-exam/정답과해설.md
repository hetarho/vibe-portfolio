# Oracle SQL~JDBC 시험 대비 정답과 해설

문제 번호는 [문제집](./문제집.md)과 같다. SQL 작성형은 동등하게 동작하는 다른 SQL도 정답이다. 각 문항은 독립적이며, 같은 이름의 테이블을 생성하거나 변경하는 문항을 순서대로 실행할 필요는 없다.

## A. 데이터베이스와 SQL 기초 (1~10)

**1. 데이터와 정보의 차이**

- **데이터**는 관찰·측정한 원래 값이다.
- **정보**는 그 데이터에 의미를 부여한 결과다.

**2. 데이터베이스의 네 가지 정의**

- (a) 운영 데이터
- (b) 공용 데이터
- (c) 통합 데이터
- (d) 저장 데이터

데이터베이스는 이 네 가지 성격을 모두 갖춘 데이터의 모음이다.

**3. DBMS의 네 가지 기능**

- 추출: 데이터를 조회한다.
- 조작: 데이터를 삽입·수정·삭제한다.
- 정의: 데이터 구조를 생성·변경·삭제한다.
- 제어: 권한·보안·백업·회복·동시성을 관리한다.

> 자주 틀리는 지점: 조작과 정의를 헷갈리기 쉽습니다. 행의 값을 바꾸면 조작, 테이블의 구조를 바꾸면 정의입니다.

**4. SQL의 원래 이름**

**Structured Query Language**

**5. SQL 명령어 분류**

- DQL: `SELECT`
- DML: `INSERT`, `UPDATE`, `DELETE`
- DDL: `CREATE`, `ALTER`, `DROP`
- TCL: `COMMIT`, `ROLLBACK`

> 자주 틀리는 지점: `SELECT`를 DML에 넣는 교재도 있습니다. 이 문제는 DQL 칸을 따로 두었으니 `SELECT`는 DQL에 씁니다.

**6. SELECT 결과의 이름**

**Result Set**(결과 집합)

**7. 기본키와 외래키의 역할**

- 기본키는 각 행을 유일하게 식별하며 NULL과 중복을 허용하지 않는다.
- 외래키는 다른 테이블의 기본키나 고유키를 참조해 테이블 사이의 참조 무결성을 지킨다.

> 자주 틀리는 지점: NOT NULL이나 UNIQUE를 따로 걸지 않았다면, 외래키 열에는 같은 값이 여러 번 들어갈 수 있고 NULL도 들어갑니다. 115번에서 다시 나옵니다.

**8. 값이 없음을 나타내는 표시**

`NULL`

> 자주 틀리는 지점: Oracle은 빈 문자열 `''`도 NULL로 취급합니다. `=`나 `<>` 같은 비교 연산자로 NULL과 비교하면 결과가 UNKNOWN입니다. 23번에서 다시 나옵니다.

**9. 수업에서 쓴 세 프로그램**

- (a) Oracle 18c XE
- (b) SQL Developer
- (c) SQL*Plus

**10. 모든 행과 모든 열 조회**

```sql
SELECT * FROM EMPLOYEE;
```

## B. 기본 SELECT와 조건 검색 (11~28)

**11. 이름과 급여만 조회**

`EMP_NAME, SALARY`

**12. 계산 열에 별칭 붙이기**

```sql
SELECT EMP_NAME, SALARY * 12 AS 연봉
FROM EMPLOYEE;
```

> 자주 틀리는 지점: 별칭에 공백이 들어가면 `AS "연 봉"`처럼 큰따옴표로 감쌉니다. 작은따옴표는 문자열 값을 뜻해서 별칭에 쓰면 오류가 납니다.

**13. DISTINCT의 역할**

- 조회 결과에서 같은 값의 중복을 제거한다.
- 여러 열을 함께 쓰면 그 열들의 조합이 같은 행을 제거한다.

> 자주 틀리는 지점: SELECT 목록에서 `DISTINCT`는 SELECT 바로 뒤에 한 번만 쓰고, 뒤에 오는 열 전체의 조합에 걸립니다. 56번의 `COUNT(DISTINCT 열)`처럼 그룹 함수 안에 쓰는 것과는 별개입니다.

**14. 중복 없는 부서 목록**

- `D1`, `D2`, `NULL` 세 행이 나온다.
- `ORDER BY`가 없으므로 행의 순서는 정해져 있지 않다.

`DISTINCT`는 NULL도 하나의 값처럼 한 행으로 남긴다.

> 자주 틀리는 지점: NULL이 결과에서 빠진다고 생각하기 쉽습니다. `COUNT(DISTINCT DEPT)`는 NULL을 빼고 계산하지만, `SELECT DISTINCT`는 NULL을 한 행으로 보여 줍니다.

**15. 급여 300만 원 이상**

`SALARY >= 3000000`

> 자주 틀리는 지점: "이상"은 `>=`, "초과"는 `>`입니다. 바로 다음 16번은 초과입니다.

**16. 두 부서 중 급여 300만 원 초과**

```sql
SELECT EMP_NAME
FROM EMPLOYEE
WHERE DEPT_CODE IN ('D5', 'D6')
  AND SALARY > 3000000;
```

`WHERE (DEPT_CODE = 'D5' OR DEPT_CODE = 'D6') AND SALARY > 3000000`으로 써도 같다.

> 자주 틀리는 지점: `IN` 대신 OR로 풀어 쓰면 OR 쪽을 반드시 괄호로 묶어야 합니다. 17번이 그 문제입니다.

**17. 의도와 다른 WHERE 조건**

**AND가 OR보다 먼저** 평가되어 급여 조건이 D6에만 걸린다. OR 쪽을 괄호로 묶어 고친다.

```sql
SELECT EMP_NAME
FROM EMPLOYEE
WHERE (DEPT_CODE = 'D5' OR DEPT_CODE = 'D6')
  AND SALARY > 3000000;
```

> 자주 틀리는 지점: 괄호가 없으면 D5 직원은 급여와 상관없이 모두 나옵니다. `DEPT_CODE IN ('D5', 'D6')`으로 고쳐도 됩니다.

**18. BETWEEN으로 범위 조회**

`BETWEEN 3000000 AND 5000000`

> 자주 틀리는 지점: 작은 값을 앞에 씁니다. `BETWEEN 5000000 AND 3000000`으로 순서를 바꾸면 오류 없이 0행이 나옵니다.

**19. LIKE의 와일드카드 두 개**

- (a) `%`
- (b) `_`

**20. 김씨 성을 가진 직원**

`LIKE '김%'`

> 자주 틀리는 지점: `=`로 비교하면 `%`도 그냥 글자로 취급됩니다. 와일드카드는 `LIKE`와 함께 써야 동작합니다.

**21. 실제 밑줄 문자를 찾는 ESCAPE**

```sql
SELECT EMP_NAME, EMAIL
FROM EMPLOYEE
WHERE EMAIL LIKE '___#_%' ESCAPE '#';
```

앞의 `_` 세 개는 각각 한 글자, `#_`는 실제 밑줄 문자다.

> 자주 틀리는 지점: `ESCAPE`로 정한 문자는 바로 뒤에 오는 `_`나 `%` 한 글자를 일반 문자로 바꿉니다. 패턴에서 찾을 일이 없는 문자를 고르면 되고, 데이터에 `#`가 들어 있어도 상관없습니다.

**22. 보너스가 NULL인 직원**

`IS NULL`

> 자주 틀리는 지점: `BONUS = NULL`은 오류 없이 실행되지만 결과가 0행입니다. 28번이 이 실수를 고치는 문제입니다.

**23. NULL 비교의 결과**

- 1. `UNKNOWN`
- 2. `UNKNOWN`
- 3. `TRUE`
- 4. `FALSE`

> 자주 틀리는 지점: WHERE는 TRUE인 행만 통과시킵니다. UNKNOWN인 행은 FALSE인 행과 똑같이 걸러집니다.

**24. 이름 뒤에 '님' 붙이기**

`|| '님'`

> 자주 틀리는 지점: Oracle의 연결 연산자는 `||`입니다. `+`로는 문자열이 이어지지 않고, `CONCAT`은 인자를 두 개까지만 받습니다.

**25. 부서를 빼는 조건의 결과**

- 실행 결과는 `ID`가 3인 한 행이다.
- `ID` 4는 **포함되지 않는다.** `DEPT`가 NULL이라 `NOT IN ('D1')`의 결과가 UNKNOWN이고, `WHERE`는 TRUE인 행만 통과시키기 때문이다.

> 자주 틀리는 지점: 부서 코드가 NULL인 행까지 원하면 `OR DEPT IS NULL`을 덧붙입니다.

**26. IN으로 세 부서 조회**

```sql
SELECT EMP_ID, EMP_NAME
FROM EMPLOYEE
WHERE DEPT_CODE IN ('D1', 'D3', 'D5');
```

**27. '수'가 들어간 이름과 보너스**

- (a) `LIKE '%수%'`
- (b) `IS NOT NULL`

> 자주 틀리는 지점: `BONUS <> NULL`로 쓰면 0행입니다. NULL이 아닌 값을 찾을 때도 `IS NOT NULL`을 씁니다.

**28. 오류 두 군데 찾기**

- `SALARY AS 월급` 뒤에 쉼표가 남아 있어 `FROM` 앞에서 문법 에러가 난다. 쉼표를 지운다.
- `BONUS = NULL`은 결과가 UNKNOWN이라 한 행도 조회되지 않는다. `BONUS IS NULL`로 바꾼다.

```sql
SELECT EMP_NAME, SALARY AS 월급
FROM EMPLOYEE
WHERE BONUS IS NULL;
```

> 자주 틀리는 지점: 쉼표 쪽은 실행하자마자 오류가 나서 찾기 쉽습니다. `= NULL`은 오류 없이 0행이 나오기 때문에 놓치기 쉽습니다.

## C. 함수 (29~52)

**29. 단일 행 함수와 그룹 함수**

- 단일 행 함수는 입력 행마다 결과를 하나씩 만든다.
- 그룹 함수는 전체 행 또는 각 그룹을 묶어 결과를 하나 만든다.

> 자주 틀리는 지점: 그룹 함수와 일반 열을 SELECT에 함께 쓰려면 GROUP BY가 필요합니다. 60번에서 다시 나옵니다.

**30. 문자 수와 바이트 수**

- (a) `LENGTH`
- (b) `LENGTHB`

영문과 한글의 실제 바이트 수는 문자 집합에 따라 달라진다.

> 자주 틀리는 지점: UTF-8로 설치한 DB에서는 한글 한 글자가 3바이트라서 `LENGTH('가')`는 1, `LENGTHB('가')`는 3입니다.

**31. SUBSTR로 자른 결과**

`BASE`

> 자주 틀리는 지점: 두 번째 인자는 시작 위치, 세 번째 인자는 가져올 글자 수입니다. 위치 번호는 1부터 시작합니다.

**32. INSTR로 두 번째 위치 찾기**

`4`

> 자주 틀리는 지점: 세 번째 인자 1은 찾기 시작할 위치, 네 번째 인자 2는 "두 번째로 나오는 것"이라는 뜻입니다.

**33. 이름의 앞 두 글자**

```sql
SELECT SUBSTR(EMP_NAME, 1, 2)
FROM EMPLOYEE;
```

**34. 문자 함수 고르기**

가) `UPPER()`, 다) `SUBSTR()`, 마) `REPLACE()`

`MOD`는 숫자 함수, `ADD_MONTHS`는 날짜 함수다.

`UPPER('oracle')`의 결과는 `ORACLE`이다.

**35. TRIM 결과**

`'SQL'`(양쪽 공백을 모두 제거한다)

> 자주 틀리는 지점: `TRIM`은 양쪽, `LTRIM`은 왼쪽, `RTRIM`은 오른쪽만 지웁니다.

**36. LTRIM과 RTRIM으로 0 지우기**

`'1200'`, `'00012'`

> 자주 틀리는 지점: `LTRIM`은 왼쪽 끝의 0 세 개만 지우고 오른쪽 끝의 0은 남깁니다. `RTRIM`은 그 반대로 오른쪽 끝의 0 두 개만 지웁니다.

**37. REPLACE 결과**

`A-B-C`

**38. 이메일의 @ 앞부분**

`INSTR(EMAIL, '@') - 1`

> 자주 틀리는 지점: `- 1`을 빼먹으면 `@`까지 함께 나옵니다. `INSTR`이 돌려주는 값이 `@`의 위치이기 때문입니다.

**39. MOD 결과**

`2`

**40. 반올림 · 버림 · 올림 · 내림**

차례대로 `125.7`, `125.6`, `126`, `-3`

> 자주 틀리는 지점: `FLOOR(-2.1)`은 -2.1보다 작거나 같은 정수 중 가장 큰 수라서 -3입니다. -2로 쓰기 쉽습니다.

**41. ROUND · TRUNC · FLOOR의 차이**

- `ROUND`는 지정한 자리에서 반올림한다.
- `TRUNC`는 지정한 자리 이후를 0 방향으로 잘라 낸다.
- `FLOOR`는 해당 수 이하의 가장 큰 정수로 내린다.
- 음수에서 `TRUNC(-2.1) = -2`, `FLOOR(-2.1) = -3`이다.

> 자주 틀리는 지점: `FLOOR`는 자릿수 인자를 받지 않고 언제나 정수로 내립니다.

**42. 현재 날짜와 시각**

`SYSDATE`

> 자주 틀리는 지점: 괄호를 붙이지 않습니다. `SYSDATE()`라고 쓰면 오류가 납니다.

**43. 입사 6개월 뒤의 날짜**

```sql
SELECT EMP_NAME, ADD_MONTHS(HIRE_DATE, 6)
FROM EMPLOYEE;
```

> 자주 틀리는 지점: `HIRE_DATE + 6`은 6일 뒤입니다. 날짜에 숫자를 더하면 일 단위로 더해집니다.

**44. 날짜 함수 세 가지**

- (a) `ADD_MONTHS`
- (b) `LAST_DAY`
- (c) `MONTHS_BETWEEN`

각 직원의 입사일이 속한 달의 마지막 날짜는 `SELECT EMP_NAME, LAST_DAY(HIRE_DATE) FROM EMPLOYEE;`로 조회한다.

> 자주 틀리는 지점: `MONTHS_BETWEEN`은 `MONTHS_BETWEEN(나중 날짜, 처음 날짜)` 순서로 씁니다. 순서를 바꾸면 음수가 나옵니다.

**45. 입사 연도만 꺼내기**

`YEAR FROM HIRE_DATE`

> 자주 틀리는 지점: 괄호 안은 `YEAR FROM HIRE_DATE` 순서이고 쉼표를 쓰지 않습니다.

**46. 날짜를 문자열로 바꾸기**

```sql
SELECT EMP_NAME, TO_CHAR(HIRE_DATE, 'YYYY-MM-DD')
FROM EMPLOYEE;
```

> 자주 틀리는 지점: 월은 `MM`, 분은 `MI`입니다. 시각까지 나오면 `YYYY-MM-DD HH24:MI:SS`로 씁니다.

**47. 형변환 함수 세 가지**

- (a) `TO_CHAR`
- (b) `TO_DATE`
- (c) `TO_NUMBER`

문자열 `'2024-03-15'`를 날짜로 바꾸는 식은 `TO_DATE('2024-03-15', 'YYYY-MM-DD')`다.

> 자주 틀리는 지점: `TO_DATE`의 앞 인자는 바꿀 문자열, 뒤 인자는 그 문자열이 어떤 형식으로 쓰였는지 알려 줍니다. 46번의 `TO_CHAR`와 인자 순서가 같습니다.

**48. NULL을 0으로 바꾸기**

`NVL(BONUS, 0)`

**49. 보너스를 포함한 연봉**

```sql
SELECT EMP_NAME,
       (SALARY + SALARY * NVL(BONUS, 0)) * 12
         AS ANNUAL_PAY
FROM EMPLOYEE;
```

> 자주 틀리는 지점: `NVL`을 빼면 보너스가 NULL인 직원은 연봉이 통째로 NULL이 됩니다. NULL이 섞인 산술 계산은 결과도 NULL입니다.

**50. DECODE로 부서 구분하기**

```sql
DECODE(DEPT_CODE, 'D1', '본부',
                  'D2', '지사',
                  '기타')
```

비교값과 결과가 짝을 지어 이어지고, 맨 마지막 하나는 어디에도 맞지 않을 때의 기본값이다.

**51. CASE로 급여 등급 매기기**

- (a) `SALARY >= 5000000`
- (b) `SALARY >= 3000000`

> 자주 틀리는 지점: 위에서부터 차례로 검사하고 처음 맞은 곳에서 멈춥니다. 그래서 큰 기준을 먼저 씁니다. (a)와 (b)를 바꿔 쓰면 500만 원도 '중'이 됩니다.

**52. 보너스를 곱한 결과**

- ID 1의 `PAY`는 `10`, ID 2의 `PAY`는 `NULL`이다.
- `200 * NULL`은 NULL이다.

## D. 정렬·집계·그룹·집합 (53~68)

**53. 두 기준으로 정렬**

`SALARY DESC, EMP_NAME ASC`

`ASC`는 기본값이라 생략해도 된다.

Oracle은 내림차순에서 NULL을 맨 앞에 둔다. 급여가 NULL인 행을 맨 뒤로 보내려면 `SALARY DESC NULLS LAST`로 쓴다.

> 자주 틀리는 지점: `DESC`는 기준마다 따로 붙습니다. 앞 열에만 `DESC`를 쓰면 뒤 열은 기본값인 오름차순입니다.

**54. WHERE와 HAVING이 거르는 대상**

- `WHERE`는 그룹을 만들기 전에 개별 행을 걸러 낸다.
- `HAVING`은 `GROUP BY` 이후 집계 결과를 기준으로 그룹을 걸러 낸다.

> 자주 틀리는 지점: `WHERE`에는 `COUNT(*)`나 `AVG()` 같은 그룹 함수를 쓸 수 없습니다. 실행 순서가 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY라서 WHERE 시점에는 그룹이 아직 없습니다.

**55. 전체 직원 수**

`COUNT(*)`

**56. COUNT의 세 가지 쓰임**

- 차례대로 `4`, `3`, `2`
- `COUNT(DEPT)`는 NULL인 행을 빼고 계산한다.

> 자주 틀리는 지점: `COUNT(DISTINCT DEPT)`도 NULL은 빼고 계산합니다. D1과 D2 두 가지만 남습니다.

**57. 부서별 직원 수**

```sql
SELECT DEPT, COUNT(*) AS CNT
FROM EXAM_EMP
GROUP BY DEPT
ORDER BY DEPT;
```

`GROUP BY`는 NULL끼리 한 그룹으로 묶는다. 오름차순 정렬에서 NULL은 맨 뒤에 온다.

> 자주 틀리는 지점: `COUNT(DEPT)`로 쓰면 NULL 그룹의 인원이 0으로 나옵니다. 실행 결과의 마지막 행이 1이므로 `COUNT(*)`를 써야 합니다.

**58. 부서별 평균 급여**

```sql
SELECT DEPT_CODE, ROUND(AVG(SALARY), 1)
FROM EMPLOYEE
GROUP BY DEPT_CODE
ORDER BY DEPT_CODE;
```

> 자주 틀리는 지점: "소수 첫째 자리까지"는 `ROUND(값, 1)`입니다. `ROUND(값)`이나 `ROUND(값, 0)`은 정수가 됩니다.

**59. 조건을 건 부서별 인원과 평균**

```sql
SELECT DEPT_CODE, COUNT(*) AS 인원,
       AVG(SALARY) AS 평균급여
FROM EMPLOYEE
WHERE SALARY >= 3000000
GROUP BY DEPT_CODE
HAVING COUNT(*) >= 2;
```

> 자주 틀리는 지점: 급여 조건은 행마다 거는 조건이라 `WHERE`, 인원 조건은 그룹에 거는 조건이라 `HAVING`입니다. 둘의 자리를 바꾸면 틀립니다.

**60. 부서별 합계가 나오지 않는 코드**

그룹 함수 `SUM`과 집계하지 않은 `DEPT_CODE`를 함께 조회하면서 그룹 기준인 `GROUP BY`를 지정하지 않았기 때문이다.

```sql
SELECT DEPT_CODE, SUM(SALARY)
FROM EMPLOYEE
GROUP BY DEPT_CODE;
```

> 자주 틀리는 지점: 이때 나오는 오류는 `ORA-00937: not a single-group group function`입니다. 메시지를 알아 두면 오류 찾기 문제에서 원인을 바로 떠올릴 수 있습니다.

**61. 표본의 부서별 급여 합계**

`(D1, 300)`, `(D2, 300)`, `(NULL, 400)` 순서다.

> 자주 틀리는 지점: 오름차순에서 Oracle은 원래도 NULL을 맨 뒤에 둡니다. `NULLS LAST`는 그 순서를 분명히 적어 둔 것입니다.

**62. 두 가지 보너스 평균**

- `AVG(BONUS)`는 `0.15`, `AVG(NVL(BONUS, 0))`는 `0.075`다.
- `AVG`는 NULL인 행을 빼고 계산하므로 첫 식은 두 행(0.1, 0.2)의 평균이고, 두 번째 식은 NULL을 0으로 바꿔 네 행의 평균을 구한다.

> 자주 틀리는 지점: `AVG`는 NULL인 행을 분모에서도 뺍니다. 0으로 바꿔 줘야 분모에 들어갑니다.

**63. 그룹 함수 고르기**

가) `MAX()`, 다) `COUNT()`, 마) `MIN()`

`ROUND`와 `NVL`은 행마다 결과를 하나씩 만드는 단일 행 함수다.

가장 높은 급여와 가장 낮은 급여를 한 행으로 조회하려면 `SELECT MAX(SALARY), MIN(SALARY) FROM EMPLOYEE;`로 쓴다.

**64. 부서별 보너스 받는 직원 수**

`COUNT(BONUS)`

`COUNT(BONUS)`는 NULL을 제외하므로, 보너스 받는 직원이 없는 부서는 0으로 남는다.

> 자주 틀리는 지점: `WHERE BONUS IS NOT NULL`로 먼저 거르면 보너스 받는 직원이 없는 부서는 그룹째 사라집니다. 문제가 "0으로 결과에 남도록"이라고 했으니 거르지 않고 `COUNT(BONUS)`로 구합니다.

**65. 집합 연산자 네 가지**

- (a) `UNION`
- (b) `UNION ALL`
- (c) `INTERSECT`
- (d) `MINUS`

> 자주 틀리는 지점: Oracle 18c의 차집합은 `MINUS`입니다. 다른 DB에서 쓰는 `EXCEPT`와 헷갈리지 않게 합니다.

**66. UNION과 UNION ALL의 행 수**

- (1) `UNION`은 **1행**이다. 중복된 1이 하나만 남는다.
- (2) `UNION ALL`은 **2행**이다.

**67. 급여 합계가 1천만 원을 넘는 부서**

```sql
SELECT DEPT_CODE, SUM(SALARY) AS TOTAL
FROM EMPLOYEE
GROUP BY DEPT_CODE
HAVING SUM(SALARY) > 10000000
ORDER BY TOTAL DESC;
```

> 자주 틀리는 지점: `HAVING`에는 별칭 `TOTAL`을 쓸 수 없고 `ORDER BY`에는 쓸 수 있습니다. HAVING은 SELECT보다 먼저, ORDER BY는 나중에 실행되기 때문입니다.

**68. GROUPING SETS로 두 기준 한 번에**

```sql
SELECT DEPT_CODE, JOB_CODE, AVG(SALARY)
FROM EMPLOYEE
GROUP BY GROUPING SETS ((DEPT_CODE, JOB_CODE),
                        (DEPT_CODE));
```

부서별 평균 행에서는 `JOB_CODE`가 NULL로 나온다.

> 자주 틀리는 지점: 안쪽 괄호 한 쌍이 그룹 기준 하나입니다. `(DEPT_CODE, JOB_CODE)`는 조합별, `(DEPT_CODE)`는 부서별 결과를 만듭니다.

## E. JOIN (69~88)

**69. JOIN을 쓰는 목적**

공통된 조건을 이용해 둘 이상의 테이블에 흩어진 열과 행을 하나의 결과로 조회한다.

**70. INNER JOIN과 LEFT OUTER JOIN**

- INNER JOIN은 짝이 맞지 않는 왼쪽 행을 결과에서 제외한다.
- LEFT OUTER JOIN은 그 행을 남기고 오른쪽 열을 NULL로 채운다.

**71. 직원과 부서명 · ANSI JOIN**

```sql
SELECT E.EMP_NAME, D.DEPT_TITLE
FROM EMPLOYEE E
JOIN DEPARTMENT D ON E.DEPT_CODE = D.DEPT_ID;
```

> 자주 틀리는 지점: 두 테이블을 잇는 열의 이름이 `DEPT_CODE`와 `DEPT_ID`로 서로 다릅니다. 이름이 달라서 `USING`은 쓸 수 없습니다.

**72. 부서 없는 직원까지 조회**

`LEFT JOIN` (`LEFT OUTER JOIN`도 정답)

부서 코드가 NULL인 직원은 `DEPT_TITLE`이 NULL로 나온다.

> 자주 틀리는 지점: Oracle 전용 문법으로는 `WHERE E.DEPT_CODE = D.DEPT_ID(+)`입니다. `(+)`는 NULL로 채워질 쪽, 곧 부서 테이블 쪽에 붙습니다.

**73. USING으로 직급명 연결**

`USING (JOB_CODE)`

> 자주 틀리는 지점: `USING`으로 이은 `JOB_CODE`를 SELECT에 쓸 때 `E.JOB_CODE`처럼 별칭을 붙이면 오류가 납니다. 그냥 `JOB_CODE`라고 씁니다.

**74. ON과 USING**

- `ON`은 원하는 조인 조건을 직접 쓴다.
- `USING(열)`은 양쪽에 이름이 같은 조인 열을 지정할 때 쓴다.
- `USING`으로 지정한 열은 결과에서 한 열로 합쳐지며, 참조할 때 테이블 별칭을 붙이지 않는다.

**75. CROSS JOIN의 행 수**

`3 × 4 = 12`행

`CROSS JOIN`은 한쪽의 모든 행을 다른 쪽의 모든 행과 하나씩 연결한다.

**76. 직원 없는 부서까지 · 부서가 왼쪽**

```sql
SELECT D.DEPT_TITLE, E.EMP_NAME
FROM DEPARTMENT D
LEFT JOIN EMPLOYEE E ON D.DEPT_ID = E.DEPT_CODE;
```

> 자주 틀리는 지점: 72번과 테이블 순서만 바뀌었습니다. 빠짐없이 남겨야 하는 쪽을 `FROM` 바로 뒤에 두고 `LEFT JOIN`을 씁니다.

**77. 직원 · 부서 · 지역 세 테이블**

- (a) `E.DEPT_CODE = D.DEPT_ID`
- (b) `D.LOCATION_ID = L.LOCAL_CODE`

> 자주 틀리는 지점: 지역은 직원과 바로 이어지지 않고 부서를 거쳐서 이어집니다. (b)가 `D.LOCATION_ID = L.LOCAL_CODE`인 이유입니다.

**78. 직원과 관리자 · SELF JOIN**

```sql
SELECT E.EMP_NAME AS 직원, M.EMP_NAME AS 관리자
FROM EMPLOYEE E
LEFT JOIN EMPLOYEE M ON E.MANAGER_ID = M.EMP_ID;
```

> 자주 틀리는 지점: 조건의 방향이 중요합니다. 직원의 `MANAGER_ID`가 관리자의 `EMP_ID`와 같아야 합니다. "관리자가 없는 직원도 포함"이라서 `LEFT JOIN`입니다.

**79. SELF JOIN과 별칭**

- 한 테이블을 역할이 다른 두 테이블처럼 연결하는 조인이다.
- 직원 `E`, 관리자 `M`처럼 서로 다른 별칭을 붙여 구분한다.

**80. 직급 코드를 함께 조회하는 JOIN**

- `JOB_CODE`가 `EMPLOYEE`와 `JOB` 양쪽에 있어서 어느 테이블의 열인지 모호하기 때문이다.
- `E.JOB_CODE`처럼 테이블 별칭을 붙여 한쪽을 지정한다.

```sql
SELECT E.EMP_NAME, E.JOB_CODE
FROM EMPLOYEE E
JOIN JOB J ON (E.JOB_CODE = J.JOB_CODE);
```

> 자주 틀리는 지점: 이때 나오는 오류는 `ORA-00918: column ambiguously defined`입니다. `EMP_NAME`은 한쪽에만 있어서 별칭이 없어도 실행되지만, 붙여 두면 읽기 쉽습니다.

**81. J2 직급 직원과 직급명**

```sql
SELECT E.EMP_NAME, E.SALARY, J.JOB_NAME
FROM EMPLOYEE E
JOIN JOB J ON E.JOB_CODE = J.JOB_CODE
WHERE E.JOB_CODE = 'J2';
```

**82. 부서 없는 직원에 '미배치' 표시**

```sql
SELECT E.EMP_NAME,
       NVL(D.DEPT_TITLE, '미배치') AS 부서명
FROM EMPLOYEE E
LEFT JOIN DEPARTMENT D ON E.DEPT_CODE = D.DEPT_ID;
```

> 자주 틀리는 지점: `LEFT JOIN`과 `NVL`이 둘 다 있어야 합니다. 그냥 `JOIN`을 쓰면 부서 없는 직원이 아예 빠져서 `NVL`이 바꿀 행이 남지 않습니다.

**83. OUTER JOIN의 세 종류**

- (a) `LEFT OUTER JOIN`
- (b) `RIGHT OUTER JOIN`
- (c) `FULL OUTER JOIN`

`OUTER`는 생략해도 된다.

**84. 급여 등급 · NON-EQUI JOIN**

`E.SALARY BETWEEN G.MIN_SAL AND G.MAX_SAL`

`=`가 아닌 조건으로 잇는 조인이라 NON-EQUI JOIN이라고 부른다.

**85. 같은 부서 직원 쌍**

```sql
SELECT A.EMP_ID, B.EMP_ID
FROM EMPLOYEE A
JOIN EMPLOYEE B
  ON A.DEPT_CODE = B.DEPT_CODE
 AND A.EMP_ID < B.EMP_ID;
```

`<` 조건으로 자기 자신과의 쌍과, 순서만 바뀐 중복 쌍을 함께 제외한다.

> 자주 틀리는 지점: `<>`로 쓰면 자기 자신과의 쌍은 빠지지만 `(A, B)`와 `(B, A)`가 둘 다 남습니다.

**86. 조인 조건을 빠뜨리면**

- 의도하지 않은 카테시안 곱이 발생해 양쪽 행의 모든 조합이 만들어질 수 있다.
- 한쪽이 N행, 다른 쪽이 M행이면 N×M행이다.

**87. 직급은 반드시, 부서는 있으면**

- (a) `JOIN` (`INNER JOIN`도 정답)
- (b) `LEFT JOIN`

> 자주 틀리는 지점: 조인마다 종류를 따로 고릅니다. 반드시 있어야 하는 직급은 `JOIN`, 없어도 남겨야 하는 부서는 `LEFT JOIN`입니다.

**88. 모든 부서의 직원 수 · 0명 포함**

직원이 없는 부서도 직원 열이 NULL인 한 행으로 남고, `COUNT(*)`는 그 행까지 1로 계산한다. `COUNT(E.EMP_ID)`로 바꾼다.

```sql
SELECT D.DEPT_ID, D.DEPT_TITLE,
       COUNT(E.EMP_ID) AS EMP_COUNT
FROM DEPARTMENT D
LEFT JOIN EMPLOYEE E ON D.DEPT_ID = E.DEPT_CODE
GROUP BY D.DEPT_ID, D.DEPT_TITLE;
```

> 자주 틀리는 지점: `LEFT JOIN` 뒤에서 인원을 구할 때는 오른쪽 테이블의 키를 `COUNT`에 넣습니다. 166번도 같은 구조입니다.

## F. SUBQUERY와 순위 (89~106)

**89. 서브쿼리란**

- 다른 SQL 문 안에 괄호로 넣는 SELECT 문이다.
- 메인 쿼리의 조건·값·조회 대상으로 사용할 수 있다.

**90. 서브쿼리의 세 가지 종류**

- 단일 행 서브쿼리는 한 행을 반환한다.
- 다중 행 서브쿼리는 여러 행을 반환한다.
- 다중 열 서브쿼리는 두 열 이상을 반환하며 행의 수와는 별개다. 다중 행이면서 다중 열일 수도 있다.

> 자주 틀리는 지점: 종류에 따라 쓰는 연산자가 다릅니다. 단일 행은 `=`·`>`, 다중 행은 `IN`·`ANY`·`ALL`, 다중 열은 `(열1, 열2) IN`이고 결과가 한 행이면 `=`도 씁니다.

**91. 평균보다 많이 받는 직원**

```sql
SELECT EMP_NAME, SALARY
FROM EMPLOYEE
WHERE SALARY > (SELECT AVG(SALARY) FROM EMPLOYEE);
```

> 자주 틀리는 지점: `WHERE SALARY > AVG(SALARY)`처럼 그룹 함수를 WHERE에 바로 쓰면 오류입니다. 평균은 서브쿼리로 먼저 구합니다.

**92. 최고 급여 직원 · 동점 포함**

```sql
SELECT EMP_NAME
FROM EMPLOYEE
WHERE SALARY = (SELECT MAX(SALARY) FROM EMPLOYEE);
```

최고 급여와 같은 급여를 받는 직원이 여럿이면 모두 나온다.

**93. D1 부서와 급여가 같은 직원**

서브쿼리가 여러 행을 반환하는데, `=`는 값 하나와만 비교할 수 있기 때문이다.

```sql
SELECT EMP_NAME
FROM EMPLOYEE
WHERE SALARY IN (SELECT SALARY
                 FROM EMPLOYEE
                 WHERE DEPT_CODE = 'D1');
```

> 자주 틀리는 지점: 이때 나오는 오류는 `ORA-01427: single-row subquery returns more than one row`입니다. `IN` 대신 `= ANY`로 써도 같은 뜻입니다.

**94. 부서별 최고 급여 · 다중 열 비교**

`(DEPT_CODE, SALARY)`

부서 코드가 NULL인 행은 `NULL = NULL`이 UNKNOWN이어서 빠진다.

> 자주 틀리는 지점: 급여만 `SALARY IN (SELECT MAX(SALARY) ... GROUP BY DEPT_CODE)`로 비교하면, 다른 부서의 최고 급여와 우연히 같은 직원까지 나옵니다. 부서·급여를 쌍으로 비교하는 이유입니다.

**95. 상관 서브쿼리와 비상관 서브쿼리**

- 상관 서브쿼리는 바깥 쿼리의 열을 참조해 바깥 행에 따라 결과가 달라진다.
- 비상관 서브쿼리는 바깥 행을 참조하지 않는다.

> 자주 틀리는 지점: 상관 서브쿼리는 바깥 행마다 새로 계산된다고 생각하면 이해하기 쉽습니다. 비상관 서브쿼리는 한 번 구한 값을 모든 행에 똑같이 씁니다.

**96. 자기 부서 평균보다 많이 받는 직원**

```sql
SELECT E.EMP_NAME, E.DEPT_CODE, E.SALARY
FROM EMPLOYEE E
WHERE E.SALARY > (
        SELECT AVG(X.SALARY)
        FROM EMPLOYEE X
        WHERE X.DEPT_CODE = E.DEPT_CODE);
```

부서 코드가 NULL인 직원은 위 비교에서 제외된다.

> 자주 틀리는 지점: 바깥과 안쪽을 별칭으로 구분해야 합니다. 별칭 없이 `DEPT_CODE = DEPT_CODE`로 쓰면 안쪽 테이블끼리 비교되어, 부서 코드가 있는 직원 전체의 평균과 비교하게 됩니다.

**97. 직원이 있는 부서만**

- (a) `EXISTS`
- (b) `E.DEPT_CODE = D.DEPT_ID`

`EXISTS`는 행이 있는지만 보므로 서브쿼리의 SELECT 목록에는 관례로 `1`을 쓴다.

**98. 직원이 없는 부서 · NOT EXISTS**

```sql
SELECT D.DEPT_TITLE
FROM DEPARTMENT D
WHERE NOT EXISTS (
        SELECT 1
        FROM EMPLOYEE E
        WHERE E.DEPT_CODE = D.DEPT_ID);
```

> 자주 틀리는 지점: `DEPT_ID NOT IN (SELECT DEPT_CODE FROM EMPLOYEE)`로 쓰면 `DEPT_CODE`에 NULL이 하나라도 있을 때 결과가 0행입니다. 바로 다음 99번이 그 이유를 묻습니다.

**99. NOT IN 서브쿼리의 결과**

- 결과는 **한 행도 없다.**
- 서브쿼리 결과 `(0.1, NULL)`에 NULL이 들어 있어 `BONUS <> NULL` 비교가 언제나 UNKNOWN이 되므로, 어떤 행도 `NOT IN` 조건을 TRUE로 통과하지 못한다.

서브쿼리에 `AND BONUS IS NOT NULL`을 넣어 NULL을 빼면 `ID` 3이 나온다. 바깥 행의 `BONUS`가 NULL인 ID 2와 4는 여전히 비교 결과가 UNKNOWN이라 빠진다.

> 자주 틀리는 지점: `X NOT IN (0.1, NULL)`은 `X <> 0.1 AND X <> NULL`과 같습니다. 뒤쪽이 언제나 UNKNOWN이라 전체가 TRUE가 될 수 없습니다. 이럴 때는 `NOT EXISTS`로 바꿔 쓰는 방법도 있습니다.

**100. 급여 상위 3명**

- (a) `SALARY DESC, EMP_ID ASC`
- (b) `ROWNUM <= 3`

급여가 NULL인 직원은 내림차순에서 맨 앞에 온다. 그런 직원이 있으면 (a)에 `NULLS LAST`를 붙인다.

> 자주 틀리는 지점: 정렬은 안쪽에서, `ROWNUM`은 바깥쪽에서 합니다. 101번이 이 순서를 거꾸로 쓴 경우입니다.

**101. 상위 3명을 보장하지 못하는 코드**

- `ROWNUM`은 `ORDER BY`보다 먼저 붙는다. 그래서 먼저 고른 임의의 3행만 나중에 급여순으로 정렬된다.
- 먼저 정렬한 인라인 뷰를 만들고, 그 바깥에서 `ROWNUM <= 3`을 적용해야 한다.

```sql
SELECT EMP_NAME
FROM (SELECT EMP_NAME
      FROM EMPLOYEE
      ORDER BY SALARY DESC)
WHERE ROWNUM <= 3;
```

**102. FROM 절에 놓인 서브쿼리**

**인라인 뷰(Inline View)**

**103. WITH 절이 하는 일**

`WITH 이름 AS (SELECT ...)`로 중간 결과에 이름을 붙여 메인 SQL에서 재사용하면 긴 서브쿼리를 반복 작성하지 않아도 된다.

```sql
WITH DEPT_AVG AS (
  SELECT DEPT_CODE, AVG(SALARY) AS AVG_SAL
  FROM EMPLOYEE
  GROUP BY DEPT_CODE
)
SELECT E.EMP_NAME, E.SALARY, A.AVG_SAL
FROM EMPLOYEE E
JOIN DEPT_AVG A ON E.DEPT_CODE = A.DEPT_CODE;
```

위 코드는 부서별 평균에 `DEPT_AVG`라는 이름을 붙여 두고 직원 테이블과 연결한 예시다.

**104. RANK와 DENSE_RANK**

- `RANK`: (a) `1`, (b) `1`, (c) `3`
- `DENSE_RANK`: (d) `1`, (e) `1`, (f) `2`

> 자주 틀리는 지점: `RANK`는 동점인 두 행을 공동 1위로 두고 다음 순위를 3으로 매기고, `DENSE_RANK`는 바로 다음 번호 2를 매깁니다. `ROW_NUMBER`는 동점이어도 1, 2, 3을 붙입니다.

**105. 부서별 급여 1위 · RANK**

```sql
SELECT EMP_NAME, DEPT_CODE, SALARY
FROM (SELECT E.EMP_NAME, E.DEPT_CODE, E.SALARY,
             RANK() OVER (
               PARTITION BY DEPT_CODE
               ORDER BY SALARY DESC NULLS LAST
             ) AS RN
      FROM EMPLOYEE E)
WHERE RN = 1;
```

`PARTITION BY`는 NULL 부서도 하나의 그룹으로 묶는다.

> 자주 틀리는 지점: `WHERE RANK() OVER (...) = 1`처럼 바로 거르면 오류입니다. 순위 함수는 SELECT 단계에서 계산되므로 인라인 뷰로 한 번 감싸고 바깥에서 거릅니다.

**106. 전체 합계의 20%를 넘는 부서**

```sql
SELECT DEPT_CODE, SUM(SALARY) AS TOTAL
FROM EMPLOYEE
GROUP BY DEPT_CODE
HAVING SUM(SALARY) > (
        SELECT SUM(SALARY) * 0.2
        FROM EMPLOYEE);
```

> 자주 틀리는 지점: `CHAR(10)`에 `'ABC'`를 넣으면 뒤에 공백 일곱 칸이 붙어 10자리로 저장됩니다.

```sql
CREATE TABLE MEMBER (

```

- (a) `DATE`
- (b) `TIMESTAMP`

**111. NOT NULL · UNIQUE · PRIMARY KEY**

- 1. NULL **불가**, 중복 **허용**
- 2. NULL **허용**, 중복 **불가**
- 3. NULL **불가**, 중복 **불가**

`UNIQUE`가 막는 것은 NULL이 아닌 값의 중복이다. NULL은 여러 행에 들어갈 수 있다.

> 자주 틀리는 지점: 기본키는 `NOT NULL`과 `UNIQUE`를 합친 것으로 외워 두면 표를 바로 채울 수 있습니다. 다만 기본키는 테이블에 하나뿐입니다.

**112. 기본키를 지정한 MEMBER**

```sql
CREATE TABLE MEMBER (
  ID   VARCHAR2(20) PRIMARY KEY,
  NAME VARCHAR2(30)
);
```

제약 조건에 이름을 붙이려면 `ID VARCHAR2(20) CONSTRAINT MEMBER_PK PRIMARY KEY`처럼 쓴다.

**113. 복합 기본키와 선언 개수**

- (a) 두 개 이상의 열을 묶어 행을 유일하게 식별하는 기본키다.
- (b) **한 개**다. 다만 그 하나를 여러 열로 구성할 수 있다.

```sql
CONSTRAINT GRADE_PK
  PRIMARY KEY (TERM_NO, CLASS_NO, STUDENT_NO)
```

복합 기본키는 열 정의를 다 쓴 뒤 테이블 수준에서 따로 선언한다. 170번이 가정하는 `TB_GRADE`의 기본키가 이런 형태다.

> 자주 틀리는 지점: `ID ... PRIMARY KEY, NAME ... PRIMARY KEY`처럼 열마다 붙이면 기본키를 두 번 선언한 것이라 오류가 납니다.

**114. TEAM과 PLAYER · 외래키**

```sql
CREATE TABLE TEAM (
  TEAM_ID NUMBER PRIMARY KEY
);

CREATE TABLE PLAYER (
  PLAYER_ID NUMBER PRIMARY KEY,
  TEAM_ID   NUMBER REFERENCES TEAM (TEAM_ID)
);
```

테이블 수준으로 쓰면 `FOREIGN KEY (TEAM_ID) REFERENCES TEAM (TEAM_ID)`다.

> 자주 틀리는 지점: 부모 테이블인 `TEAM`을 먼저 만들어야 합니다. 아직 없는 테이블은 참조할 수 없습니다.

**115. 외래키 열에 넣을 수 있는 값**

- 1. 가능
- 2. **불가능** (부모 테이블에 없는 값이다)
- 3. 가능 (`NOT NULL`이 없다)
- 4. 가능 (외래키는 중복을 막지 않는다)
- 5. **불가능** (그 행을 참조하는 자식 행이 있다)

> 자주 틀리는 지점: 99를 넣으면 `ORA-02291: integrity constraint (계정.제약이름) violated - parent key not found`가 납니다.

**116. ON DELETE SET NULL과 CASCADE**

- `ON DELETE SET NULL`: 자식 행은 남기고 외래키 값을 NULL로 바꾼다.
- `ON DELETE CASCADE`: 참조 중인 자식 행도 함께 삭제한다.

> 자주 틀리는 지점: 둘 다 쓰지 않았을 때의 기본 동작은 삭제 거부입니다. 자식 행이 참조하고 있는 부모 행은 지울 수 없습니다.

**117. 나이를 0 이상으로 제한**

`CHECK (AGE >= 0)`

`AGE`의 NULL까지 막으려면 `NOT NULL`도 추가해야 한다.

> 자주 틀리는 지점: `CHECK`는 조건이 FALSE일 때만 막고 UNKNOWN은 통과시킵니다. 그래서 NULL은 `CHECK (AGE >= 0)`에 걸리지 않습니다.

**118. 열에 주석 달기**

`COMMENT ON COLUMN`

> 자주 틀리는 지점: 테이블에 다는 주석은 `COMMENT ON TABLE MEMBER IS '회원'`입니다. `ON COLUMN` 뒤에는 `테이블.열`을 씁니다.

**119. 열 추가**

`ADD`

**120. 열 크기 변경**


> 자주 틀리는 지점: 길이를 늘리는 변경은 자료형의 최대 길이 안에서라면 보통 바로 됩니다. 줄일 때는 이미 들어 있는 값이 새 길이 안에 들어가야 합니다. 문제가 그 가정을 붙인 이유입니다.

**121. ALTER TABLE의 네 가지 키워드**

- (a) `ADD`
- (b) `MODIFY`
- (c) `DROP COLUMN`
- (d) `RENAME COLUMN … TO`

`MEMBER`의 `PHONE` 열을 삭제하는 SQL은 `ALTER TABLE MEMBER DROP COLUMN PHONE;`이다.

> 자주 틀리는 지점: `ADD`와 `MODIFY`는 열 하나면 괄호를 생략해도 되고, 여러 열이면 괄호로 묶습니다. `DROP COLUMN` 뒤에는 괄호 없이 열 이름 하나만 씁니다.

`RENAME COLUMN NAME TO MEMBER_NAME`

`ADD CONSTRAINT MEMBER_PK`

> 자주 틀리는 지점: 다른 제약 조건은 `ADD CONSTRAINT`로 추가하지만 `NOT NULL`만은 `MODIFY (ID NOT NULL)`로 바꿉니다.

## H. DML과 트랜잭션 (127~138)

**127. INSERT · UPDATE · DELETE**

- `INSERT`: 행을 추가한다.
- `UPDATE`: 기존 행의 값을 수정한다.
- `DELETE`: 행을 삭제한다.

**128. 열 목록을 쓴 INSERT**

```sql
INSERT INTO MEMBER (ID, NAME, AGE)
VALUES ('u1', '가람', 20);
```

> 자주 틀리는 지점: 문자는 작은따옴표로 감싸고 숫자는 그대로 씁니다. `"가람"`처럼 큰따옴표를 쓰면 열 이름으로 읽혀 오류가 납니다.

**129. 열 목록을 생략할 때**

- 테이블의 **모든 열**에 정의된 열 순서대로 값을 넣어야 한다.
- 열이 추가되거나 순서가 달라지면 의도와 다른 결과나 오류가 생길 수 있다.

**130. 조회 결과를 다른 테이블에 넣기**

```sql
INSERT INTO EMP_D1 (EMP_ID, EMP_NAME)
SELECT EMP_ID, EMP_NAME
FROM EMPLOYEE
WHERE DEPT_CODE = 'D1';
```

> 자주 틀리는 지점: 조회 결과로 넣을 때는 `VALUES`를 쓰지 않습니다. `INSERT INTO ... SELECT ...`가 한 문장입니다.

**131. 한 회원의 나이 수정**

```sql
UPDATE MEMBER
SET AGE = 21
WHERE ID = 'u1';
```

**132. 18세 미만 회원 삭제**

```sql
DELETE FROM MEMBER
WHERE AGE < 18;
```

> 자주 틀리는 지점: "미만"은 18을 포함하지 않으므로 `<`입니다. "이하"라면 `<=`입니다.

**133. WHERE가 빠진 UPDATE와 DELETE**

- `UPDATE`는 모든 행의 지정 열을 바꾼다.
- `DELETE`는 모든 행을 삭제한다.

> 자주 틀리는 지점: 커밋하기 전이라면 `ROLLBACK`으로 되돌릴 수 있습니다. 실습에서는 같은 조건으로 `SELECT`를 먼저 실행해 보고 나서 `UPDATE`나 `DELETE`를 실행하는 습관을 들입니다.

**134. DELETE와 TRUNCATE**

- 둘 다 행을 없애고 테이블 구조는 남긴다.
- `DELETE`는 DML이라 확정 전에는 `ROLLBACK`할 수 있다.
- `TRUNCATE`는 DDL이고 암묵적으로 커밋되므로 `ROLLBACK`으로 복구할 수 없다.

> 자주 틀리는 지점: `DROP TABLE`은 구조까지 없앱니다. 셋을 한 줄로 정리하면 DELETE는 커밋 전이면 되돌릴 수 있고, TRUNCATE는 되돌릴 수 없고, DROP은 테이블까지 사라집니다.

**135. 확정과 되돌림**

- (a) `COMMIT`
- (b) `ROLLBACK`

**136. ROLLBACK 뒤에 남는 행**

- (1) `0`. 확정하기 전의 삽입이 `ROLLBACK`으로 취소된다.
- (2) `1`. `CREATE TABLE` 같은 DDL을 실행하면 자동으로 커밋되어, 뒤의 `ROLLBACK`으로 삽입을 되돌릴 수 없다.

> 자주 틀리는 지점: (2)처럼 중간에 DDL이 끼면 그 자리에서 자동 커밋이 일어납니다. `TRUNCATE`를 롤백할 수 없는 것도 같은 이유입니다.

**137. 평균 급여로 갱신**

```sql
UPDATE EMPLOYEE
SET SALARY = (SELECT AVG(SALARY) FROM EMPLOYEE)
WHERE EMP_ID = 100;
```

> 자주 틀리는 지점: `SET SALARY = AVG(SALARY)`처럼 그룹 함수를 바로 쓰면 오류입니다. 평균은 서브쿼리로 구해서 넣습니다.

**138. 조건부 INSERT ALL**

```sql
INSERT ALL
  WHEN DEPT_CODE = 'D1' THEN
    INTO EMP_D1 (EMP_ID, EMP_NAME)
    VALUES (EMP_ID, EMP_NAME)
  ELSE
    INTO EMP_OTHER (EMP_ID, EMP_NAME)
    VALUES (EMP_ID, EMP_NAME)
SELECT EMP_ID, EMP_NAME, DEPT_CODE
FROM EMPLOYEE;
```

> 자주 틀리는 지점: `WHEN`에서 쓰는 `DEPT_CODE`도 맨 아래 SELECT 목록에 있어야 합니다. 대상 테이블에 넣지 않는 열인데도 SELECT에 들어가는 이유입니다.

## I. SEQUENCE (139~146)

**139. 시퀀스의 역할**

- 다음 번호를 순차적으로 만드는 데이터베이스 객체다. 키 값 발급 등에 쓴다.
- 시퀀스 값은 롤백해도 되돌아가지 않으므로 빈 번호가 생길 수 있다.

**140. 시퀀스 만들기**

- (a) `START WITH`, (b) `INCREMENT BY`
- (c) `MAXVALUE`, (d) `NOCYCLE`

100, 105, 110을 발급한 뒤 다음 `NEXTVAL`은 오류가 난다.

> 자주 틀리는 지점: 옵션 사이에는 쉼표를 넣지 않습니다. 줄을 바꾸거나 띄어 쓰기만 합니다.

**141. NEXTVAL과 CURRVAL**

- `NEXTVAL`은 시퀀스를 증가시켜 다음 값을 발급한다.
- `CURRVAL`은 현재 세션에서 마지막으로 발급받은 값을 반환한다.

**142. NEXTVAL을 세 번 호출하면**

`10`, `13`, `16`

> 자주 틀리는 지점: 첫 `NEXTVAL`은 시작값 10 그대로입니다. 처음부터 3을 더해 13으로 쓰기 쉽습니다.

**143. 새 세션에서 조회한 CURRVAL**

- `CURRVAL`은 현재 세션에서 마지막으로 발급받은 값을 돌려준다.
- 이 세션에서는 아직 `NEXTVAL`을 한 번도 호출하지 않아 돌려줄 값이 없다.

먼저 `SELECT SEQ_TEST.NEXTVAL FROM DUAL;`을 실행한 뒤에 `CURRVAL`을 조회한다.

> 자주 틀리는 지점: 이때 나오는 오류는 `ORA-08002: sequence SEQ_TEST.CURRVAL is not yet defined in this session`입니다.

**144. 시퀀스 값으로 INSERT**

`SEQ_MEMBER.NEXTVAL`

**145. 증가값 바꾸기**

```sql
ALTER SEQUENCE SEQ_TEST INCREMENT BY 10;
```

**146. 시작값을 새로 정하려면**

- 1. 가능, 2. 가능, 3. **불가능**, 4. 가능
- 시작값을 새로 정하려면 기존 시퀀스를 삭제한 뒤 새 시작값으로 다시 생성한다.

```sql
DROP SEQUENCE SEQ_TEST;
CREATE SEQUENCE SEQ_TEST START WITH 200;
```

다시 만들 때는 증가값·최댓값 같은 다른 옵션도 함께 다시 적어야 한다. 적지 않으면 기본값으로 돌아간다.

> 자주 틀리는 지점: `START WITH`만 넣은 `ALTER SEQUENCE`는 `ORA-02283` 오류입니다. Oracle 18c에는 `ALTER SEQUENCE SEQ_TEST RESTART START WITH 200;`도 있지만, 수업 자료 기준의 답은 삭제 후 다시 생성입니다.

## J. JDBC (147~160)

**156. PreparedStatement와 Statement**

- `PreparedStatement`는 SQL에 `?`를 놓고 `setString`, `setInt` 등으로 값을 바인딩한다.
- 같은 SQL 구조에 값을 바꿔 넣기 쉽고, 사용자 입력을 SQL 문법과 분리해 SQL 삽입 위험도 낮춘다.

**157. PreparedStatement로 INSERT**

```java
String sql =
    "INSERT INTO MEMBER (ID, NAME) VALUES (?, ?)";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, id);
ps.setString(2, name);
int count = ps.executeUpdate();
ps.close();
return count;
```

> 자주 틀리는 지점: `?`에는 따옴표를 붙이지 않습니다. `'?'`로 쓰면 물음표라는 글자가 들어갈 뿐이고, 값을 바인딩할 자리는 사라집니다.

**158. PreparedStatement의 두 가지 오류**

- 자리표시자 번호는 **1부터** 시작한다. `ps.setString(1, id)`로 바꾼다.
- `executeUpdate()`는 `int`를 반환한다. SELECT는 `ResultSet`을 반환하는 `executeQuery()`로 실행해야 하므로 `ResultSet rs = ps.executeQuery();`로 바꾼다.

```java
ps.setString(1, id);
ResultSet rs = ps.executeQuery();
```

> 자주 틀리는 지점: `executeUpdate()`는 `int`를 돌려주기 때문에 `ResultSet`에 담는 줄은 컴파일부터 되지 않습니다. 번호 0은 실행해야 드러나는 오류입니다.

**160. 전체 건수 조회와 자원 닫기**

```java
stmt.close();

```

```java
System.out.println(
    rs.next() ? rs.getString("NAME") : "없음");
rs.close();
ps.close();
```

`SQLException`은 메서드 선언의 `throws`로 호출자에게 넘기고, 전달받은 `conn`은 닫지 않는다.

> 자주 틀리는 지점: 결과가 있는지는 `rs.next()`의 반환값으로 판단합니다. `executeQuery()`는 결과가 0행이어도 비어 있는 `ResultSet`을 돌려주기 때문에 `rs == null`로는 확인할 수 없습니다.
